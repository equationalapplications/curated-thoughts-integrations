## 0. Summary

A third sibling integration that connects Curated Thoughts to **Claude Code**
(Anthropic's agent CLI, `claude`). It ships the same four layers every
integration provides — registration, health checks, import pre-flight, skills —
adapted to Claude Code's *plugin directory* format: a `.claude-plugin/plugin.json`
manifest, a `hooks/hooks.json` declaring a `SessionStart` hook, and
`skills/<name>/SKILL.md` files that Claude Code namespaces as
`/curated-thoughts:<name>`.

Unlike DeepSeek (a TypeScript port), this integration is **Python**, like Hermes.
Four of the five shipped scripts (`ct_env.py`, `ct_status.py`, `ct_preflight.py`,
and most of `ct_doctor.py`) are *copies* of the Hermes files, not rewrites —
CONTRIBUTING's no-cross-integration-imports rule means copying is the only
sanctioned form of sharing, and the CI architecture gate enforces it. The genuinely
new surface is small: doctor check 7, the session-start hook, and the installer.

Everything in this document is a proposal. The maintainer's sign-off on scope is
the gate for opening the implementation PR (CONTRIBUTING, "Review gates").
§11 collects the questions that need an answer before that PR opens.

## 1. Purpose and non-goals

Give a Claude Code session the same Curated Thoughts memory surface a Hermes
session already has:

- the `curated-thoughts-mcp --mcp` sidecar reachable as an MCP server in the
  session (`/mcp` shows it connected, 14+ tools);
- a fast (<200 ms) health snapshot injected into context at session start, so
  the agent knows before its first tool call whether CT memory is usable;
- a nine-check doctor for install verification, with actionable fix hints;
- import pre-flight that catches the curated-thoughts PR #188 provenance hazard
  before an agent trusts an imported brain;
- three skills (`usage`, `ops`, `sidecar`) carrying the same model-facing
  guidance Hermes and DeepSeek ship.

**Non-goals (v0.1.0):**

- No Curated Thoughts core changes. No new MCP tools. No sidecar changes.
- No changes to `integrations/hermes/` or `integrations/deepseek/`. In particular
  this PR does **not** touch `shared/compat.yaml` — see §11 Q4, which asks the
  maintainer whether 2.10's larger tool surface deserves a new tier. Changing
  compat.yaml changes every integration and belongs in its own PR.
- No Claude Code plugin *marketplace* entry. The v0.1.0 install path is
  `--plugin-dir` plus an MCP registration; a marketplace listing is a follow-up
  once the plugin has been dogfooded (§10).
- No fix for Hermes issue #14 (the real-sidecar test isolation leak). This
  integration must not *inherit* the bug — that is Task 6 of the plan — but
  fixing it in Hermes is a separate PR.

```text
├── hooks/

│   └── session-start.py            # drains stdin, prints additionalContext, always exits 0
├── scripts/
│   ├── ct_env.py                   # copied from hermes, unchanged
│   ├── ct_status.py                # copied from hermes, unchanged
│   ├── ct_preflight.py             # copied from hermes, byte-identical (see §7)
│   ├── ct_doctor.py                # copied from hermes; check 7 replaced (see §7)
│   ├── _compat_generated.py        # generated by tools/ct_ci.py generate — never hand-edited
│   └── install.sh                  # new; mirrors the Hermes installer's discipline
├── skills/
│   ├── usage/SKILL.md
│   ├── ops/SKILL.md
│   └── sidecar/SKILL.md
└── tests/
    ├── test_manifest.py            # plugin.json ↔ integration.yaml version agreement
    ├── test_ct_doctor.py           # copied from hermes; registration tests rewritten
    ├── test_hook.py                # new: the SessionStart hook as a subprocess
    ├── test_install.py             # copied + adapted from hermes
    └── test_skills_content.py      # new; mirrors deepseek's test_skills_content.ts
```

Note what is **absent** relative to Hermes: there is no `__init__.py` and no
`plugin.yaml`. Hermes loads a Python module and calls `register(ctx)`; Claude Code
loads a *directory* and reads JSON manifests. There is no code entry point to
write — the hook script is the only executable the harness invokes.

There is also no `.mcp.json`, for the reason argued in §4/D1.

## 3. Plugin shape — what Claude Code loads

A Claude Code plugin is a directory containing:

```text
<plugin>/
├── .claude-plugin/plugin.json   # name, version, description, author, license
├── .mcp.json                    # optional: MCP servers the plugin registers
├── hooks/hooks.json             # e.g. SessionStart hook → runs a command
└── skills/<name>/SKILL.md       # becomes /<plugin-name>:<name>
```

`${CLAUDE_PLUGIN_ROOT}` expands to the plugin directory inside `hooks.json` and
`.mcp.json`. On Windows, hook commands run under Git Bash.

### 3.1 `.claude-plugin/plugin.json`

```json
{
  "name": "curated-thoughts",
  "version": "0.1.0",
  "description": "Curated Thoughts memory integration for Claude Code: MCP sidecar registration, health checks, import pre-flight, and usage skills.",
  "author": { "name": "Equational Applications LLC" },
  "license": "MIT",
  "homepage": "https://github.com/equationalapplications/curated-thoughts-integrations",
  "keywords": ["memory", "mcp", "knowledge-graph"]
}
```

This is the `version_mirror` target: `version_mirror: .claude-plugin/plugin.json#version`.
`tools/ct_ci_policy.read_mirror` splits on `#`, resolves the filename relative to
the integration directory (so a subdirectory is fine), and parses `.json` with the
stdlib `json` module — verified in [`tools/ct_ci_policy.py`](../../../tools/ct_ci_policy.py).
No generator change is needed to support this mirror (D5 in §11).

### 3.2 `hooks/hooks.json`

```json
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup|resume|clear|compact",
        "hooks": [
          {
            "type": "command",
            "command": "python3 \"${CLAUDE_PLUGIN_ROOT}/hooks/session-start.py\" || python \"${CLAUDE_PLUGIN_ROOT}/hooks/session-start.py\"",
            "timeout": 10
          }
        ]
      }
    ]
  }
}
```

Two details carry weight:

- **The `python3 || python` fallback.** Windows installs of Python routinely lack
  a `python3` on PATH; POSIX installs routinely lack a bare `python`. The hook
  script itself is fail-open, so the worst case of the fallback firing twice is a
  second silent exit 0.
- **Quoting `${CLAUDE_PLUGIN_ROOT}`.** The repository checkout path can contain a
  space, and so can the sidecar path (see §5.1). Every interpolation of a path in
  this integration is double-quoted, without exception.

`SessionStart` hooks cannot block session startup, which lines up exactly with
CONTRIBUTING rule 5 (fail open). The hook is advisory context, nothing more.

### 3.3 Skills

Claude Code namespaces plugin skills as `/<plugin>:<skill>`, taking the skill
name from the containing directory. Keeping Hermes's directory names would give
users `/curated-thoughts:curated-thoughts-usage`. The directories are therefore
`usage/`, `ops/`, `sidecar/` — see D2 in §11, which asks the maintainer to confirm
the frontmatter treatment that follows from this.

## 4. Install path — registration

**Registration goes through `claude mcp add`, not a plugin-shipped `.mcp.json`.**

A plugin's `.mcp.json` is static JSON. The only sidecar reference it can express
is `"command": "curated-thoughts-mcp"`, which resolves through PATH. On the
platform where Curated Thoughts is most commonly installed for this harness —
Windows — the sidecar is **not on PATH**: it lives beside the app executable at
`%LOCALAPPDATA%\Curated Thoughts\curated-thoughts-mcp.exe`. A PATH-based
registration is dead on arrival there.

That is also a direct conflict with this repository's own rule:
[`docs/process-matching.md`](../../process-matching.md) and doctor check 2 both
say **disambiguate the sidecar by path, never by name**. A name-based MCP
registration is exactly the "two same-named binaries" trap the `sidecar` skill
warns about.

So `scripts/install.sh` resolves the absolute sidecar path using the same
discovery order `ct_env.find_sidecar()` uses, and registers it at user scope:

```bash
claude mcp add --scope user curated-thoughts -- "<abs path to sidecar>" --mcp
```

which writes `mcpServers.curated-thoughts` into `~/.claude.json`. The equivalent
JSON block is printed too, for users who prefer to edit config themselves or to
register at project scope via a repo-local `.mcp.json`:

```json
{
  "mcpServers": {
    "curated-thoughts": {
      "command": "<abs path to sidecar>",
      "args": ["--mcp"]
    }
  }
}
```

Plugin *enablement* is separate from MCP registration and stays manual in v0.1.0:
`claude --plugin-dir "<abs plugin dir>"` for a single session, or an
`enabledPlugins` entry in `~/.claude/settings.json`. The installer prints both;
it does not edit `settings.json`.

This split mirrors Hermes exactly — the installer touches the harness's config,
the plugin ships hooks and skills — and it is why the doctor's registration check
has a hard half and a soft half (§7, D4).

## 5. `ct_status.py` — the session-start probe

Copied from Hermes unchanged. Its contract is unchanged too: fast (<200 ms
target), read-only, fail-open; it never spawns the sidecar (that costs an MCP
handshake) and never opens `brain.db`. It answers only "is this wired up, and is
the brain where it is supposed to be". Deep verification is the doctor's job.

`hooks/session-start.py` is the Claude Code adapter around it:

1. Resolve the scripts directory from `CLAUDE_PLUGIN_ROOT`, falling back to this
   file's own location so the script also works when run directly.
2. Drain stdin — Claude Code sends a JSON payload there, and leaving it unread
   can leave the writer blocked. None of its fields are needed.
3. Call `ct_status.context_section()`.
4. Print exactly one line:

```json
{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"## Curated Thoughts\n…"}}
```

5. Exit 0. Always. Any exception anywhere in steps 1–4 exits 0 having printed
   nothing.

The emitted block is the same text Hermes injects: `## Curated Thoughts`, then
either "Memory sidecar ready (brain: …)" or the DEGRADED variant with up to three
notes, then the tool-routing reminder. One source of truth, three harnesses.

### 5.1 The Windows path-with-a-space hazard

On a 2.10.1 install the sidecar path is
`%LOCALAPPDATA%\Curated Thoughts\curated-thoughts-mcp.exe`. The space is not
incidental — it is in the product name, so it is in every Windows install.
Every place a path is interpolated must quote it: the `claude mcp add` line, the
printed JSON, the hook command. The acceptance criterion for this is behavioural
rather than textual: `claude mcp list` must report the server **connected**, which
only happens if the quoting survived (plan Task 9, check B3).

`ct_env._windows_candidates()` already lists both `<LOCALAPPDATA>\Programs\Curated Thoughts\`
and `<LOCALAPPDATA>\Curated Thoughts\`, and the Hermes doctor found the 2.10.1
sidecar at the second. No change is needed there. One cosmetic wrinkle is noted
as §11 Q3.

## 6. `ct_preflight.py` — import pre-flight

Copied from Hermes **byte-for-byte**, with one added line in the module docstring
recording its provenance ("copied from integrations/hermes; keep logically
identical"). The DeepSeek spec (§6) already establishes that this logic is
harness-agnostic and that the ports must stay logically identical; for a
same-language sibling, "logically identical" collapses to "identical", so the
review gate is simply `diff`.

It is the one file listed under `policy.allow_sqlite_readonly`, and the
architecture gate will re-verify on this copy what it verifies on the Hermes
original: every `sqlite3.connect(...)` opens a `mode=ro` URI with `uri=True`.

## 7. `ct_doctor.py` — nine checks

Copied from Hermes. The check list, its order, and its names are a public
contract (`check --json` consumers depend on it), and eight of the nine entries
are unchanged. Only the seventh is harness-specific:

| # | Name | Change |
|---|------|--------|
| 1 | `sidecar-binary` | none |
| 2 | `sidecar-identity` | none |
| 3 | `sidecar-mcp` | none |
| 4 | `brain-dir` | none |
| 5 | `vault` | none |
| 6 | `embedding-backend` | none |
| 7 | `claude-code-registration` | **replaces `hermes-registration`** |
| 8 | `import-preflight` | none |
| 9 | `version-compat` | none |

Removed with check 7: `HERMES_CONFIG`, `_plugin_listed_under_enabled`, and
`check_hermes_registration`. Added:

```python
CLAUDE_CONFIG = Path(
    os.environ.get("CLAUDE_CONFIG_PATH", str(Path.home() / ".claude.json"))
)
CLAUDE_SETTINGS = Path.home() / ".claude" / "settings.json"
MCP_SERVER_KEY = "curated-thoughts"
PLUGIN_NAME = "curated-thoughts"
```

`check_claude_code_registration(cwd=None)` parses `~/.claude.json` with the
stdlib `json` module — no regex scanning, because unlike Hermes's YAML this file
is JSON and the stdlib can read it properly. Verdicts:

- **FAIL** — file missing, or `mcpServers.curated-thoughts` absent. The hint is
  the exact `claude mcp add --scope user curated-thoughts -- "<path>" --mcp`
  one-liner with the discovered path substituted, plus the JSON block.
- **PASS (with a note)** — a project-level `.mcp.json` in `cwd` registers the
  server. Claude Code supports project scope, and a user who registered there has
  a working install; the doctor must not call that broken.
- **WARN** — registered, but `args` does not include `--mcp`.
- **WARN** — registered, but `command` resolves to a dev build
  (`ct_env.looks_like_dev_build`, reused unchanged).
- **WARN, never FAIL** — registered correctly, but plugin enablement cannot be
  confirmed: no key starting with `curated-thoughts@` under `enabledPlugins` in
  `~/.claude/settings.json`. This is deliberately soft. A `--plugin-dir` install
  is *invisible* to that file, so a FAIL here would fire on a perfectly working
  setup. The detail text says so explicitly rather than leaving the user to guess.
- **PASS** — registered with `--mcp`, an installed-looking command, and
  enablement confirmed.

The `CLAUDE_CONFIG_PATH` environment variable exists so tests can redirect the
config without depending on `HOME`/`USERPROFILE` semantics, which differ between
POSIX and Windows (the Hermes suite skips a test for exactly this reason). It is
not a `CURATED_*` variable, so it is outside the three-variable environment
contract and does not trip the architecture gate's env rule.

## 8. `scripts/install.sh` — idempotent, no sudo

POSIX bash, `set -euo pipefail`, shellcheck-clean (`checks.shell` runs it in CI).
Same discipline as the Hermes installer: print by default, write only under
`CT_INSTALL_EDIT=1`, never overwrite an existing entry, never move or delete user
files.

1. **Resolve the sidecar.** `command -v curated-thoughts-mcp` first, then the
   platform candidate list that mirrors `ct_env.py` — macOS app bundle, Linux
   `/usr/bin`, `/usr/local/bin`, `~/.local/bin`, `/opt/curated-thoughts`, and on
   Windows **both** `$LOCALAPPDATA/Programs/Curated Thoughts/curated-thoughts-mcp.exe`
   and `$LOCALAPPDATA/Curated Thoughts/curated-thoughts-mcp.exe`. `CLAUDE_CT_SIDECAR`
   overrides everything. Not found is a WARN, not an exit: the script continues
   and prints the registration block with a placeholder path plus the releases URL.
2. **Print the registration two ways** — the `claude mcp add` command line and the
   JSON block for `~/.claude.json` or a project `.mcp.json`. Both quote the path.
3. **Print how to enable the plugin** — `claude --plugin-dir "<abs plugin dir>"`
   now, the marketplace line later.
4. **With `CT_INSTALL_EDIT=1` and `claude` on PATH**: probe `claude mcp get
   curated-thoughts` first; register only if absent. Never edit `~/.claude.json`
   directly, never overwrite an existing entry. A second run says "already
   present — nothing changed."
5. **Finish** with the verification step:
   `python3 <plugin>/scripts/ct_doctor.py check`.

Note what the installer does *not* do, in contrast to Hermes: it does not copy
the plugin tree anywhere. Claude Code loads a plugin from wherever it lives
(`--plugin-dir`), so there is no `~/.hermes/plugins/`-style destination, no
merge-copy, no junk pruning, and none of the symlink hazards that logic carries.
The Claude Code installer is strictly smaller.

## 9. Skills

Three files, bodies **verbatim** from Hermes:

| Hermes | Claude Code | Invoked as |
|---|---|---|
| `skills/curated-thoughts-usage/SKILL.md` | `skills/usage/SKILL.md` | `/curated-thoughts:usage` |
| `skills/curated-thoughts-ops/SKILL.md` | `skills/ops/SKILL.md` | `/curated-thoughts:ops` |
| `skills/curated-thoughts-sidecar/SKILL.md` | `skills/sidecar/SKILL.md` | `/curated-thoughts:sidecar` |

The bodies are model-facing guidance about tool routing, write paths, OKF
frontmatter and sidecar lifecycle — none of it harness-specific, which is why
DeepSeek ported them verbatim too.

One paragraph is genuinely harness-specific and must change: `ops/SKILL.md`'s
**"Registration in Hermes"** section, which names `~/.hermes/config.yaml`,
`mcp_servers.curated-thoughts` and `plugins.enabled`. It becomes **"Registration
in Claude Code"**: `~/.claude.json` under `mcpServers`, `/mcp` to verify, plugin
enablement via `--plugin-dir` or the marketplace, and a note that a project-level
`.mcp.json` is equally valid. The ops skill's numbered check list also gets check
7 renamed to match the doctor.

`tests/test_skills_content.py` pins the invariants: each file has frontmatter with
a `description`; the three rules ("one sidecar", "never touch the vault
out-of-band", "fail open") each appear; no `~/.hermes` or `config.yaml` string
survives; no absolute paths.

## 10. Testing and CI

`integration.yaml` flips to `status: implemented` in the implementation PR, which
puts the integration in the `discover` matrix:

```yaml
matrix:
  os: [ubuntu-latest, macos-latest, windows-latest]
  python: ["3.9", "3.13"]

checks:
  test: python -m unittest discover -s tests
  lint: ruff check --select E9,F63,F7,F82,F401 .
  shell:
    - scripts/install.sh
```

Three OSes × two interpreters, matching Hermes. The code is stdlib-only, so the
interpreter range *is* the compatibility surface; 3.9 in the matrix means no
`match`, no runtime `X | Y` unions, and `from __future__ import annotations` at
the top of every module.

### 10.1 Windows must be green, not skipped

Hermes currently skips 28 tests on Windows, most of them because its mock sidecar
is an extensionless shebang script that Windows `CreateProcess` cannot execute
(WinError 193) and `shutil.which` will not resolve. This integration ships an
additional `curated-thoughts-mcp.bat` next to the Python mock, containing
`@python "%~dp0mock_sidecar.py" %*`, so the MCP-spawn tests run on Windows too.
Skips are kept only for tests that assert POSIX-absolute candidate paths and for
`install.sh` (a bash script; Windows runners have no bash on PATH).

### 10.2 Hermetic against a real install (the issue #14 class)

Hermes issue #14: with a real sidecar installed, its suite fails — the test
`PATH` still contains the directory holding the real `curated-thoughts-mcp`, so
`shutil.which` finds the installed binary instead of the mock and points a live
sidecar at a fixture brain. Reproduced on the development machine on 2026-09-11
(`FAILED (failures=5, skipped=28)`; `OK` before the install).

This integration must not inherit it. `DoctorTestCase.setUp` builds the subprocess
`PATH` as the fake bin directory plus only those inherited directories that do
**not** contain a `curated-thoughts-mcp`. A developer with Curated Thoughts
installed gets a green suite, and `ct_doctor.py --self-test` exits 0 on a machine
with a live sidecar — acceptance criterion A8.

Fixing #14 in Hermes is a separate, welcome PR; this spec only asserts the new
integration does not copy the bug.

### 10.3 Gates

The repository gates are unchanged and all apply:

| Gate | Relevance here |
|---|---|
| `validate` | `integration.yaml` against `shared/integration.schema.json` |
| `generate --check` | `scripts/_compat_generated.py` current; never hand-edited |

## 11. Decisions and open questions for the maintainer

The five decisions below are the spec's recommendations. D1, D2 and D4 carry
explicit questions; D3 and D5 are stated for the record and need only a nod.

**D1 — Register via `claude mcp add`, not a plugin `.mcp.json`.** Recommended,
argued in §4: a `.mcp.json` can only name the binary, PATH-based resolution fails
on Windows, and name-based disambiguation contradicts `docs/process-matching.md`.

> **Q1: Accept the `claude mcp add` path for v0.1.0?** The alternative is to ship
> `.mcp.json` with `command: curated-thoughts-mcp` for a one-step
> `/plugin install`, and let doctor check 1 tell Windows users to add the sidecar
> directory to PATH. That trades a working default for a nicer install story. A
> `.mcp.json` variant can also be added later without breaking the `mcp add`
> path — they are not mutually exclusive.

**D2 — Plugin name `curated-thoughts`; skill directories `usage`, `ops`,
`sidecar`.** Claude Code derives the skill name from the directory, so Hermes's
directory names would produce `/curated-thoughts:curated-thoughts-usage`.

> **Q2: Is "bodies verbatim, frontmatter adapted" the right fidelity?** The
> recommendation is to keep each body byte-identical to Hermes (except the
> Registration paragraph in `ops`, §9) and drop the frontmatter `name:` key so
> Claude Code uses the directory name. The alternative is to keep the frontmatter
> identical to Hermes too, accepting either the doubled namespace or a mismatch
> between the declared name and the directory.

**D3 — The `SessionStart` hook is a Python script invoked via a `python3 ||
python` fallback**, registered for matchers `startup|resume|clear|compact`. It
drains stdin, calls `ct_status.context_section()`, prints the `additionalContext`
JSON, and always exits 0 (§5).

**D4 — Doctor check 7 is `claude-code-registration`**, with the verdict table in
§7: FAIL only on "not registered at all", PASS for a project-scope `.mcp.json`,
and WARN-not-FAIL when plugin enablement cannot be confirmed.

> **Q3: Is WARN the right verdict for unconfirmable plugin enablement?** A
> `--plugin-dir` session leaves no trace in `~/.claude/settings.json`, so the
> check cannot distinguish "not enabled" from "enabled in a way this file does not
> record". Hermes FAILs the equivalent condition only because its config file is
> authoritative; Claude Code's is not.

**D5 — `version_mirror: .claude-plugin/plugin.json#version`.** Verified
supported: `read_mirror` handles subdirectories and `.json` files
([`tools/ct_ci_policy.py`](../../../tools/ct_ci_policy.py)). No tooling change
needed.

> **Q6: a Hermes test forbids `CLAUDE_PLUGIN_ROOT` repository-wide, and this
> integration must read it.** `integrations/hermes/tests/test_install.py`'s
> `RepoWideContractTests.test_claude_plugin_root_is_never_read` walks **every**
> text file in the repository — `REPO = INTEGRATION.parents[1]` — and fails if any
> of them matches `environ(\.get)?[\(\[]\s*["']CLAUDE_PLUGIN_ROOT`. It was written
> when Hermes was shedding a Claude Code-shaped plugin layout it had inherited by
> mistake, and its reasoning ("Hermes sets `PLUGIN_ROOT`, so any expansion of
> `CLAUDE_PLUGIN_ROOT` silently resolves to an empty path under Hermes") is about
> Hermes, not about the repository. `hooks/session-start.py` in this integration
> must read exactly that variable — it is how Claude Code tells a plugin where it
> lives.
>
> The natural fix is one line in that Hermes test: scope `_repo_text_files()` to
> `INTEGRATION` instead of `REPO`, keeping the guard's real intent (no
> `CLAUDE_PLUGIN_ROOT` *inside Hermes*) while letting siblings use their own
> harness's variables. That is a test-only change, exempt from the version gate —
> but it is still a change under `integrations/hermes/`, which this spec otherwise
> commits not to touch.
>
> **Which is preferred: scope the guard in this PR's sibling implementation PR, a
> separate one-line Hermes PR first, or something else?** This blocks Task 4.

### Observations from the live 2.10.1 install (not blocking, but worth a decision)

> **Q4: should `shared/compat.yaml` grow a tier for 2.10?** The installed sidecar
> (Curated Thoughts 2.10.1) answers `tools/list` with **16** tools, not the 14
